# 开源发布问题清单与实施计划

更新日期：2026-10-19。

本计划面向维护者，将开源发布前的问题拆成 27 项可实施任务，覆盖评测、数据集制作、
测试、范例与发布交付。目标是让外部用户无需修改库源码，就能用自己的路径完成
数据处理、批量评测、产物保存和报告生成，并能验证结果的计算口径。

仓库已有统一 Runner、组件注册、格点 IO、数据契约、合成资料测试、批量执行和基础报告。
实施应复用这些能力，优先修复配置失效、数据错配和缓存复用问题，再逐步收拢重复编排。
本清单依据代码静态核查；其中的触发场景是实施时应补充的回归用例，不表示本次已运行验证。

## 优先级与任务执行规则

- **P0：发布前处理。** 涉及错误结果、覆盖丢失、安装不可用或发布授权。对应能力若暂不发布，应明确排除并限制入口。
- **P1：首批改进。** 影响外部用户跑通、配置可理解性、失败诊断和维护效率。
- **P2：逐步重构。** 在结果基线稳定后推进，避免与数值口径修改混在同一 PR。

每项任务可直接拆为 Issue。提交 PR 时应包含问题中的触发场景、最终行为和验收证据。
只为高风险数学、数据错配、配置失效及完整处理链增加有价值的回归；普通文件拆分复用原有验证。
下文标为“拟新增”的模块、字段和命令均为目标设计，当前不能直接当作现有接口运行。

## 一 架构与职责边界

### A01 收拢通用 Runner 与专用串行流程

**P1；已确认。** 定位：[serial.py](../pipelines/evaluation/serial.py)、[runner.py](../pipelines/evaluation/runner.py)、[cli.py](../pipelines/evaluation/cli.py)。

**问题与影响：** `run_serial_evaluation` 自己完成读取、配对、指标构建、状态合并与落盘，
并直接限制 Fengqing/CRA；通用 Runner 另有一套编排。两处修改可能产生不同的指标选择、样本口径和输出行为。

**实施步骤：**

1. 列出两入口在 `valid_time/init_lead`、成员处理、参考场、区域和产物上的差异，保留专用入口当前基线。
2. 补齐通用流程确实缺少的业务语义，通过统一 SourceSpec、配对和指标接口表达。
3. 在相同口径已对表后，将旧入口改为通用 Runner 的兼容包装；保留原返回类型，另行安排弃用。

**验收：** 同一小型 Fengqing/CRA 输入通过两入口得到相同评分键、有效样本数、单位与容差内数值；旧入口不再自行维护样本循环和文件读取。
**依赖：** C01、C02；涉及指标选择时依赖 B02。不要先删旧入口再补结果基线。

### A02 按业务拆分大型协议模块

**P2；已确认职责集中，具体提取边界需实施时确认。** 定位：[protocols.py](../pipelines/evaluation/protocols.py)、[execution/plan.py](../pipelines/evaluation/execution/plan.py)。

**问题与影响：** `protocols.py` 集中格点、站点和台风业务，计划层还直接导入其中的业务辅助函数。
新增一种业务时需要理解和修改较大的共享模块。

**实施步骤：** 按格点、站点、台风拆分协议实现；把各业务共用的时间选择与请求构建函数提取为小模块；
先保留原导入路径的转发。协议负责准备与配对样本，执行器继续负责样本循环和状态归并。

**验收：** 原配置与注册名继续有效；拆分前后评分、样本计数和产物列一致；无新增循环依赖。
**依赖：** C01、C02。此任务只移动职责，不同时修改算法或默认参数。

### A03 整理 TY 的读取与算法边界

**P1；按 TY 指台风处理。** 定位：[typhoon.py](../datakit/evaluation/typhoon.py)、[babj_reader.py](../datakit/evaluation/adapters/babj_reader.py)、[track_error.py](../datakit/evaluation/metrics/track_error.py)。

**问题与影响：** 台风已通过模板、协议、指标和 writer 接入统一评测；实际问题是 `typhoon.py`
同时承担 BABJ 报文解析、中心诊断、几何和误差计算。`track_error.py` 与协议都依赖其中的函数。

**实施步骤：** 将 BABJ 原始解码移入 `datakit.io.readers`，适配器只构造标准数据契约；
将中心诊断与误差几何分别归入明确的算法模块；梳理 `match_errors` 与指标实现的调用关系，
确认哪些仅兼容旧口径，哪些应共享，保留必要的旧路径转发。

**验收：** 确定性与集合台风归档对表不变；GBK、北京时转换、首时效种子、缺实况及成员聚合口径有对应验证。
**依赖：** C01、C02。保留业务独立模块，不以合成一个大文件作为验收标准。

### A04 补齐外部组件注册和类型检查

**P1；已确认注册机制存在，但扩展链路不完整。** 定位：[registry.py](../datakit/evaluation/registry.py#L162)、[components.py](../pipelines/evaluation/components.py)、[cli.py](../pipelines/evaluation/cli.py)。

**问题与影响：** 程序化注册已支持自定义组件；CLI 尚无明确的外部注册初始化入口。
`Registry.build` 调用 `get` 后直接执行工厂，没有使用 `validate_reference` 的组件类型检查；
带完整前缀的组件名需要防止绕过预期类型约束。

**实施步骤：** 构建前统一检查实际组件类型；先提供“外部脚本显式导入注册模块，再调用公开 API”的最小范例。
如确需 CLI 插件加载，再增加显式模块列表，并说明配置与模块必须来自可信代码。

**验收：** 在仓库外注册一个自定义 reader 或 metric 后可以运行；把 `metric.rmse` 放到 reader 位置时，在读取资料前给出字段明确的配置错误。
**依赖：** B02、F04。首版无需引入插件发现框架。

## 二 数据接入与配置

### B01 修复参数声明与实际构建不一致

**P0；已确认参数未传入。** 定位：[components.py](../pipelines/evaluation/components.py#L131)、[layouts.py](../datakit/io/readers/layouts.py)、[DailyClimatologyReader](../datakit/evaluation/adapters/daily_climatology_reader.py)。

**问题与影响：** `_fengqing_source` 接收配置字典，但没有将 `step_hours` 传给 `_gridded_source`；
FuXi 工厂却会传入。修改 Fengqing 配置中的步长不能按预期改变布局。
日序气候态 reader 支持 `chunk_points`，工厂也没有透传，配置中的同名参数不会生效。

**实施步骤：** 逐个核对公开参数与工厂构造实参；统一步长覆盖逻辑；将计划支持的 `chunk_points`
显式透传并校验为正值，未承诺支持的参数则明确拒绝；输出解析后的有效参数。

**验收：** 将 `step_hours` 改为 3 后，构造出的布局和有效时刻按 3 小时解释；缺省值保持兼容。
改变 `chunk_points` 能改变读取块预算，结果数值保持一致；拼错参数必须报错。
**依赖：** 无；可以先作为一个小修复 PR。

### B02 明确指标启停并增加执行前校验

**P0 处理必要参考场缺失；P1 完成配置校验。** 定位：[spec.py](../pipelines/evaluation/spec.py#L129)、[config.py](../pipelines/evaluation/config.py)、[plan.py](../pipelines/evaluation/execution/plan.py#L68)、[acc.py](../datakit/evaluation/metrics/acc.py#L56)。

**问题与影响：** `PipelineSpec.metrics` 总是遍历模板中的指标，`metric_options` 只覆盖参数；
从配置路由中删除 ACC 不会真正停用它。ACC 缺少参考场时会使用零场继续计算，最终标为 `PARTIAL`
并附警告，仍可能被用户误读为正常的距平相关结果。

**实施步骤：**

1. 选定一种显式指标选择方式，例如拟新增 `enabled_metrics`；缺省沿用模板集合，空列表与未配置的含义明确区分。
2. 先解析最终指标与变量路由，再计算所需资料；禁用指标不应触发参考场读取。
3. 在发现大批资料前验证源参数、时间范围、指标名、变量路由、writer 和必要参考源；未知参数拒绝或给明确弃用提示。
4. 正式 ACC 缺参考时尽早失败，并在指标直接调用时再次检查；合成参考只用于明确标记的演示或测试。

**验收：** “只选 RMSE 且无气候态”可运行；“选 ACC 但无参考”读取前失败；未知指标或路由拼写错误能定位到字段。
**依赖：** 无；与 B01 分开提交，避免小参数修复被整体配置重构阻塞。

### B03 让布局扩展可以在库外完成

**P1；已确认部分绑定。** 定位：[components.py](../pipelines/evaluation/components.py#L58)、[layouts.py](../datakit/io/readers/layouts.py)、[Era5ZarrReader](../datakit/evaluation/adapters/era5_zarr_reader.py)。

**问题与影响：** 已有 `GriddedLayout`，但内置工厂直接绑定某个布局；ERA5 reader 构造函数接受 layout，
工厂只传入 source_id 与 stores。换目录规则或通道命名时，外部用户缺少清晰的接入方式。

**实施步骤：** 先支持外部 Python 脚本构造布局并注册通用源；为布局明确目录模板、文件模式、
成员、变量映射、单位与时间语义的字段。确有纯数据配置需求时，再增加受校验的字典解析；内置模型布局保留为预设。

**验收：** 在库外用不同目录、变量名和通道名接入一个小型数据源，复用 RMSE 配对与计算；不修改内置模型分支。
**依赖：** B02、A04 的程序化注册范例。

### B04 完成专用 Reader 与 IO 的职责分离

**P2；已确认部分共用、部分仍直接解码。** 定位：[execution/sources.py](../pipelines/evaluation/execution/sources.py)、[era5_zarr_reader.py](../datakit/evaluation/adapters/era5_zarr_reader.py)、[daily_climatology_reader.py](../datakit/evaluation/adapters/daily_climatology_reader.py)、[datakit/io](../datakit/io)。

**问题与影响：** 通用格点读取和部分气候态已复用 IO；ERA5 专用 store 解析、日序气候态读取仍位于评测适配器，
其他数据处理流程难以直接复用。迁移时还要避免把气候态平滑等科学处理一并塞入底层 IO。

**实施步骤：** IO 负责文件发现、解码和资源关闭；适配器负责变量、单位、时间语义与 DataBundle；
加载层负责切片与缓存。按 ERA5、日序气候态、BABJ 逐源迁移；日序索引和平滑保留独立语义函数。
一般 xarray Zarr 与项目特有的裸数组 store 分别保留解码器，共享上层契约。

**验收：** IO 可独立读出同一份原始资料；经适配后与旧链路的值、坐标、单位和时间一致；IO 不反向依赖评测流程。
**依赖：** C01、C02；先做一个数据源试点，再推广。

### B05 统一统计文件优先级并按通道标签对齐

**P0；已确认实现不一致及标签重赋值。** 定位：[_datasets.py](../pipelines/dataset/_datasets.py#L55)、[_conversion.py](../pipelines/dataset/_conversion.py#L263)。

**问题与影响：** `_load_sidecar` 优先读取外部 NC/NPY，而 `_load_channel_statistic` 优先读 Zarr 数组。
后者主要检查长度，最后直接 `assign_coords`；当文件中的通道顺序与请求不同，数值可能被贴上错误标签。
前者在已有标签无法匹配时也可能回退为按位置读取。此问题会影响归一化与反归一化结果。

**实施步骤：**

1. 统一统计加载入口及来源优先级；多来源冲突时拒绝或要求显式选择，并记录实际来源。
2. 已有标签的统计必须按名称选择和重排；缺失、重复或无法对应的标签报错，不能仅检查长度。
3. 无标签 NPY 允许按位置读取时，要求声明其原始通道顺序。

**验收：** 数据通道为 `[t2m, z500]`、统计标签为 `[z500, t2m]` 时能正确重排；同长度错误标签必须失败；
NC、NPY 和 Zarr 同时存在且冲突时行为一致；归一化再反归一化能恢复原值。
**依赖：** 无；保留一份旧行为样本用于评估兼容影响。

### B06 修复同一天多个时次的拆文件冲突

**P0；已确认文件名未包含时次。** 定位：[split_netcdf_by_time_and_channel](../pipelines/dataset/__init__.py#L103)。

**问题与影响：** 函数逐 time 索引写出，但文件名只有 `YYYYMMDD.nc`。输入同一天有 00、06 时次时，
`overwrite=False` 会中途失败，`overwrite=True` 会让后一个时次覆盖前一个。

**实施步骤：** 首先确定公开契约：若定位为日文件，按日期分组并在一个文件中保留当天全部 time；
若定位为逐时次文件，则文件名加入小时，必要时加入分钟和秒。写入前一次性校验完整目标列表中的重名和冲突。

**验收：** 输入同一天多个时次，读回后每个时次都在；重复 timestamp 和已有文件按明确策略处理；
参数校验失败时不留下已写出一半的文件。
**依赖：** 无；这是数据完整性修复，优先于目录调整。

## 三 测试覆盖与科学正确性

### C01 建立功能覆盖矩阵

**P1；当前无法从测试清单证明全部覆盖。** 定位：[tests](../tests)、[templates.py](../pipelines/evaluation/templates.py)、[components.py](../pipelines/evaluation/components.py)。

**问题与影响：** “上游测试已迁移”“pytest 没报错”和“所有公开能力已验证”是不同结论。
真实资料跳过、合成数据对表和独立公式验证也需要分别标明。

**实施步骤：** 拟新增 `docs/TEST_COVERAGE_MATRIX.md`，以业务能力为行，记录公开入口、数据源、
配置、指标、执行模式、输出、现有用例、基线来源及缺口。先填实际支持的组合，不枚举无意义的全排列。

| 能力 | 已见验证 | 首先补齐的缺口 |
| --- | --- | --- |
| 格点确定性与集合 | 真实资料回归、合成执行回归 | 指标选择、缺参考、线程和时效切块边界 |
| 站点降水 | 分类与概率真实资料回归 | 不依赖私有资料的累计窗口到评分完整链路 |
| 台风确定性与集合 | 种子、路径与归档对表 | 小型公开可再造输入及异常样本 |
| 数据源适配 | 格点元数据、气候态 IO 与适配一致性 | 自定义布局、缺通道、单位与时间边界 |
| 数据集制作 | ERA5/ORAS5 转换及部分错误输入 | 通道错配、统计来源冲突、多时次拆分 |
| 批量评测与报告 | 已有执行和报告实现 | 命令行到任务清单、报告文件及图片的闭环 |
| 安装与发布 | 已有依赖和构建声明 | wheel 在仓库外运行公开入口 |

**验收：** 每个承诺支持的功能都有“已验证／待验证／资料缺失／不支持”状态和对应证据；
不以测试函数数量代替覆盖结论。
**依赖：** 无，是重构前应先完成的清单。

### C02 补高风险数值与处理口径基线

**P1。** 定位：[metrics](../datakit/evaluation/metrics)、[matching.py](../datakit/evaluation/matching.py)、[transforms](../datakit/transforms)。

**问题与影响：** 部分真实资料预期值是框架回归基线，不能独立证明算法正确；所有实现共享同一错误时，互相对表仍可能通过。

**实施步骤：** 按 C01 的缺口选择可手算或独立参考的样本：加权 RMSE/Bias、centered 与 uncentered ACC、
列联表 TS/POD/FAR、概率阈值与 BSS 基准、降水累积缺步、集合缺成员、台风距离与方向。
验证单位转换只执行一次，统一记录 NaN、零权重、零方差及全缺测的行为。

**验收：** 每项新增基线说明公式、输入、期望值和容差来源；区分“数学正确性”与“保持旧归档一致”；
串行、分块、进程在同一采样口径下对表，不要求所有浮点结果逐位相同。
**依赖：** C01；覆盖对应重构模块后再执行 A01、A02、B04。

### C03 将最小完整链路设为必跑回归

**P0 建立发布门禁；后续扩展为 P1。** 定位：[test_weather_field_execution.py](../tests/evaluation/integration/test_weather_field_execution.py)、[conftest.py](../tests/evaluation/integration/conftest.py)。

**问题与影响：** 已有进程与串行一致、相同配置 resume 的合成回归；尚未检出报告产物的直接验证，
相同配置重跑也无法验证缓存是否在配置改变后失效。

**实施步骤：** 先用一个确定性小样本完成公开入口到 CSV、manifest、报告和图片的闭环；
增加“相同配置确实复用缓存”和“改变阈值、变量、参考或输入后拒绝旧缓存”的高价值用例。
再补线程、跨日窗口和部分失败；用实际调用计数或明确的缓存命中记录证明复用，不能只比较两次结果相同。

**验收：** 无私有目录也能运行；核对关键数值、评分键、样本数、配置记录和报告图片引用；
必跑环境缺少约定依赖时应使门禁失败，不能全跳过后通过。
**依赖：** 首个报告用例依赖 D02、E05；缓存变更用例依赖 E01。

### C04 管理真实资料与独立参考来源

**P1。** 定位：[integration/README.md](../tests/evaluation/integration/README.md)、各 `*_realdata.py`。

**问题与影响：** 不同测试使用不同路径覆盖方式，部分默认路径固定；资料缺失会跳过。
目前的说明也明确部分基准值尚未完成独立参考脚本复核。

**实施步骤：** 统一资料根入口，并保留必要的逐源覆盖；记录每套资料的版本、时间、网格、变量、来源和可分发性。
把参考分成“独立算法”“外部归档”“本框架回归”；为内部真实资料验收提供严格模式，缺约定资料即失败。

## 五 结果追溯与运行可靠性

### E01 为 resume 增加配置与输入指纹

**P0；已确认缓存命中没有兼容性校验。** 定位：[execute_chunks](../pipelines/evaluation/execution/executor.py#L453)、[_outcome_path](../pipelines/evaluation/execution/executor.py#L665)。

**问题与影响：** 缓存路径只包含 `seg序号_时间块.pkl`，读取后主要检查 `cached.ok`。
在相同输出目录改变指标参数、变量、参考场或原地更新输入，可能复用旧状态；调整流程段顺序也有同类风险。
现有 orphan 提示只能发现块名不再属于计划，不能发现同名块的口径变化。

**实施步骤：**

1. 给缓存封装增加 schema 版本和稳定摘要；摘要覆盖解析后的指标、变换、协议、布局、变量与采样范围、组件版本及输入身份。
2. 文件输入至少记录规范路径、大小和修改时间，并写清它不是内容校验；有强复现需求时支持内容摘要或数据版本。
   Zarr 按 store 版本或选定元数据与数据版本记录，不能只依赖目录时间戳。
3. 命中前逐项校验；不兼容则重算并记录原因。无摘要旧缓存按不兼容处理。
4. 临时文件完整写入后原子替换；加载后验证类型和 schema，损坏缓存不作为已完成任务。

**验收：** 同一配置确实命中；改变阈值、单位布局、成员、参考或输入版本时旧缓存失效；
流程段换序不误用；中断写入不会让下次运行误判成功。
**依赖：** 首版可独立修复；再与 E02 共用配置标准化逻辑。

### E02 保存全部流程段的有效配置与来源

**P1；已确认只完整保存第一段。** 定位：[Runner._persist](../pipelines/evaluation/runner.py#L183)、[ReportWriter._write_manifest](../pipelines/evaluation/reporting/writer.py#L153)。

**问题与影响：** `resolved_config = asdict(spec)` 使用第一段 spec；后续段仅摘要记录 pipeline、protocol、window。
manifest 的主要 summary 也取第一段，不能完整表达各段独立的输入和执行语义。

**实施步骤：** 引入 manifest schema 版本；按稳定 segment_id 保存每段最终指标、变换、布局、采样、输入索引和执行参数；
汇总字段明确为各段合并还是第一段。记录包版本、可获得的提交版本、Python 与关键依赖版本、带时区的时间戳。
传入多个 spec 时，检查不能共用一次落盘上下文的冲突字段。

**验收：** 两段窗口或参数不同的运行，manifest 能逐段恢复有效配置；脱离 Git 安装时仍能记录包版本；
旧版 manifest 仍能生成报告，缺失信息明确显示。
**依赖：** 无；segment_id 的规则与 E01 对齐。

### E03 明确目录覆盖并保证核心产物完整提交

**P1；已确认直接覆盖核心文件。** 定位：[ReportWriter.write](../pipelines/evaluation/reporting/writer.py#L80)、[report.py](../pipelines/evaluation/reporting/report.py)。

**问题与影响：** `scores.csv`、派生视图和 manifest 按顺序直接写到目标目录；后续 writer 失败时，
目录可能混合新评分与旧 manifest。重跑报告时也可能留下旧图。

**实施步骤：** 定义已存在结果的策略：默认拒绝、显式覆盖或新 run 目录；resume 缓存与最终结果分开管理。
核心产物先在暂存位置完整写入，全部成功后以目录替换或带完成指针的版本目录提交；
仅逐文件原子替换不足以保证整组一致。清理旧报告只依据产物索引，不扫描删除用户文件。

**验收：** 模拟派生 writer 失败后，旧完整结果仍可用或新运行明确未完成；不存在新 CSV 配旧 manifest 的“成功目录”；
重复运行遵循文档中的覆盖策略。
**依赖：** E02。实现先限定本地文件系统，与当前项目范围一致。

### E04 区分完整成功 部分成功 与失败

**P1；已确认存在结果不完整但进程成功的路径。** 定位：[_sample_loop](../pipelines/evaluation/execution/executor.py#L218)、[Runner._finalize](../pipelines/evaluation/runner.py)、[cli.py](../pipelines/evaluation/cli.py#L22)。

**问题与影响：** 样本循环除 `MetricError` 外广泛捕获异常；部分指标已经积累后，后续异常可能仍保留前面结果。
缺变量指标可能只给 warning；部分块失败会记入 manifest，但只要 Runner 返回，CLI 的 `run_evaluation` 仍返回 0。
使用者难以从退出码知道承诺的任务是否完整完成。

**实施步骤：** 将配置与程序错误直接上抛，包括样本内部的 ConfigError；允许跳过的资料错误使用明确异常类型。
按样本与指标记录预期、成功、缺失和失败计数；明确采用每指标部分提交还是整样本提交。
增加严格与允许部分完成的策略，并将 run_status 写入 manifest 与批量任务记录；CLI 按策略给退出码。

**验收：** 一个时效缺资料、一个变量缺失、一个指标异常分别得到可区分的状态；严格模式不能以退出码 0 掩盖缺项；
允许部分完成时保留有效产物并显示原因和数量。
**依赖：** B02、C01、E02。

### E05 明确基础报告支持范围并验证输出

**P1；基础报告存在，验证与特殊业务展示待补。** 定位：[build_report](../pipelines/evaluation/reporting/report.py#L9)、[track_error.py](../datakit/evaluation/metrics/track_error.py)、[reporting/views.py](../pipelines/evaluation/reporting/views.py)。

**问题与影响：** 基础报告只对 `status=success` 且 value、lead_h 可转换为数值的记录绘图；
没有可绘图记录时仍可生成报告。台风逐时效曲线位于专项产物，通用 lead 曲线不足以代表全部台风报告能力。
跨任务汇总也不能默认把不同样本和单位的数值合并比较。

**实施步骤：** 定义报告结果状态和过滤原因统计；对部分成功显示明确提示；
先支持格点、站点已有长表视图，台风报告显式读取其专项时效表或声明范围。
批量报告首版只汇总任务状态与链接；跨模型比较另行要求一致样本、区域、阈值、单位和算法版本。

**验收：** 非交互环境生成 REPORT.md 和 PNG，所有图片引用存在；空结果、全失败和缺列行为可预期；
区域和阈值不混组；报告重建不执行评分。
**依赖：** E02；专项台风图可作为后续独立 PR，不阻塞首个格点闭环。

## 推荐的批量范例组织

以下为拟新增结构；职责以复用现有代码为前提：

```text
examples/evaluation/
├── demo_data.py                 # 普通资料生成函数，不依赖 pytest
├── run_batch.py                 # 配置列表、路径覆盖与公开 API 调用
└── configs/                     # 各任务数据与计算配置
pipelines/evaluation/
├── batch.py                     # 任务调度、状态持久化、报告调用
├── runner.py                    # 单次任务执行，继续复用现有内核
└── reporting/                   # 已有评分表与报告实现
tests/evaluation/integration/
└── test_batch_report.py         # 通过公开入口验证上述完整流程
```

建议产物组织：

```text
results/<batch_id>/
├── tasks.json                   # 各任务配置标识、状态、错误与产物
├── REPORT.md                    # 状态汇总与各任务报告链接
├── field_task/
│   ├── scores.csv
│   ├── manifest.json
│   └── report/REPORT.md          # 图片放同目录
└── station_task/
    ├── scores.csv
    ├── manifest.json
    └── report/REPORT.md
```

单任务继续沿用 EvalConfig → specs_from_config → Runner；批量层只管理任务间的组织。
推荐补充一个返回 ResultBundle 的公开函数，CLI 保持退出码包装；不要让批量层重新实现读取、配对或指标计算。
参数覆盖应生成独立配置副本，避免任务之间共享字典造成相互修改。

首版演示目标命令，待 D01、D02 实现后才可执行：

```bash
python -m examples.evaluation.run_batch --synthetic --output-dir ./results/demo
python -m examples.evaluation.run_batch --reports-only ./results/demo
```

真实资料模式接受外部配置列表及明确的路径覆盖；不要假设所有源都只有 root_dir，ERA5 还需要 stores 映射。

| 5 完成发布交付 | F01、F02、F03 最小门禁 | 许可证、wheel、CI 验证记录 | 仓库外安装与公开闭环通过 |
| 6 逐步整理架构 | C02 对应基线、A01、A03、B03、A04、B04、A02、D03、E03 | 按职责拆分的小 PR 与扩展教程 | 每步兼容旧入口并保持约定数值口径 |

表内批次体现依赖顺序，不要求串行等待整个批次结束。例如 D02 可以从第一批开始；
E03 的核心写入完整性也可在 E02 后提前处理。A04 的类型检查可独立修复，完整插件加载不是首发前提。

第一轮建议先提交五个具体 PR：测试矩阵与文档清理、参数透传、通道统计对齐、多时次拆分、resume 指纹。
它们能直接降低后续重构风险，并为完整演示提供可信的底座。

## 开源发布验收清单

- [ ] 发布范围、代码来源、许可证和演示资料授权明确。
- [ ] wheel 可在仓库外运行外部配置；文档声明的依赖组合有实际验证。
- [ ] 合成资料范例覆盖读取、处理、评分、落盘、报告与任务索引。
- [ ] 配置变更实际生效；未知字段、缺少必要参考和指标选择错误可尽早定位。
- [ ] 统计按通道标签正确对齐，同一天多个时次不会因文件命名而丢失。
- [ ] resume 校验配置与输入身份，不会把旧状态当作新口径结果。
- [ ] 每个流程段的有效配置与来源可追溯，完整成功与部分成功可区分。
- [ ] 公开能力的测试状态明确；必跑 CI 没有通过跳过全部用例来获得成功。
