记录日期：2026-10-19。

更细的代码定位、实施步骤、依赖与验收条件见
[开源发布问题清单与实施计划](OPEN_SOURCE_ACTION_PLAN.md)，共拆分为 27 项任务。

本文记录本次讨论中的问题、待核实事项和拟议方向，不代表重构方案已确认，
也不表示相关功能已经实现。实施前先确认职责边界与对外接口。

## 开源发布的六类改进

仓库已有 IO、数据适配、指标、Runner、组件注册和报告模块，主要改进方向是
使现有分层落实到各条业务链路，并让外部用户能独立安装、运行和验证结果。
以下结合代码静态检查归类；测试覆盖结论仍需覆盖矩阵与实际运行结果支持。

| 大类 | 当前问题与证据 | 改进目标 |
| --- | --- | --- |
| 架构与职责边界 | `Runner` 与 `serial.py` 各自组织评测；`protocols.py` 集中多类业务。TY 已有统一协议、指标和输出视图，但 `typhoon.py` 同时包含 BABJ 解析、路径诊断和误差算法。 | 明确唯一推荐执行入口；逐步复用公共编排；读取、业务配对、指标和报告各负其责。 |
| 数据接入与配置 | Fengqing/CRA 工厂绑定内置布局；专用串行入口直接限制这两个源；样例仍有个人资料路径；模板固定指标集合，配置中的变量路由不等于启停指标。 | 外部路径、布局和变量规则可显式配置；指标选择与参数覆盖语义清楚；缺少必要参考场时尽早报错。 |
| 测试与科学正确性 | 已有合成数据测试、执行模式对表与真实资料回归；真实资料缺失会跳过。测试目录未检出 `build_report` 或 `REPORT.md` 的直接验证；测试指南引用的 `tests/test_regression.py` 当前不存在。 | 建立功能覆盖矩阵；用小资料验证公开入口到报告的闭环；数学高风险项使用独立预期值；区分通过、跳过和未覆盖。 |
| 范例与使用文档 | 已有单次 Fengqing 评测与报告范例，以及 `run_evaluations` 批量执行能力；缺少覆盖新结构的多任务完整范例、任务清单与报告索引。 | 新用户只改路径即可批量运行；提供无私有资料也能运行的演示；补充新数据源和新指标的接入范例。 |
| 结果追溯与运行可靠性 | 已有 `scores.csv`、manifest、配置记录和部分失败记录；多段 Runner 的 `resolved_config` 当前只序列化第一段，批量入口主要靠日志汇总状态。 | 保存每段有效配置、代码版本及资料标识；持久化各任务状态；明确目录覆盖、部分成功和重跑策略。 |
| 开源交付与维护 | 仓库当前未见许可证文件、贡献指南或提交到仓库的 CI 配置；`pyproject.toml` 未声明许可证。按配置名加载依赖仓库 `examples/`，而包发现仅包含 `datakit*` 和 `pipelines*`。 | 发布前确认代码与样例资料的授权并补许可证；建立贡献、版本和 CI 规则；验证 wheel 安装后的公开入口及依赖组合，明确示例是否随包交付。 |

对“指标各自携带整套系统”的表述需要收窄：例如 `metrics/rmse.py` 已按
`accumulate / merge / finalize` 计算，没有承担文件发现和任务调度。
重点应查公共编排的重复、业务协议过大，以及指标对参考场和输出结构的隐式依赖。

建议按以下顺序形成可验收的工作项：

1. **建立基线**：列清已支持业务、入口、配置、测试和报告，保留现有数值回归基线；发布前完成授权与许可证确认。
2. **打通外部使用**：提供可配置路径的最小合成资料批量范例，从读取、评分、落盘到报告索引形成闭环，并纳入 CI。
3. **逐步收拢设计**：确定推荐执行入口，整合 IO 与适配职责，拆分过大的业务协议，明确指标启停及参考场要求；每步与基线对表。
4. **完成发布验收**：在干净环境从 wheel 安装运行，检查声明的 Python 和依赖组合、文档命令、产物追溯与贡献流程。

发布验收以“外部用户无需修改库源码即可运行公开范例并验证产物”为核心；
重构范围按实际重复与扩展需求确定。

## 二、具体问题

### E01：TY 的独立文件与整合边界

用户提出：TY 为什么还单独拎出一个文件，没有合进去？

- 待确认“TY”的具体文件和含义；若指台风，重点检查
  `datakit/evaluation/typhoon.py`、`metrics/track_error.py` 和通用协议中的台风逻辑。
- 需要核实未整合的是算法、读取器、流程入口、测试还是报告能力。
- 独立文件本身不等于未整合，应确认它是否复用了统一数据契约、执行入口和产物格式。
- 根据职责决定保留独立业务模块，还是消除重复入口；不要只为减少文件数量合并代码。

代码核查：台风已通过 `templates.py` 中的 `weather_typhoon_det/ens`、
`protocols.py` 中的台风协议、`metrics/track_error.py` 和 `typhoon_cases` writer
接入统一流程。当前可确认的问题是 `typhoon.py` 混有报文解析和算法职责；
是否还存在用户所指的其他 TY 文件，需要结合具体文件确认。

验收：明确 TY 在统一流程中的位置、调用方式、输入输出，以及仍需补齐的能力。

### E02：测试是否覆盖全部功能

现有迁移验证了上游集成测试用例的保留，不等于已经证明全部功能被覆盖。
真实资料缺失导致的跳过，也不能计作数值正确性验证。

待建立覆盖矩阵：

- 业务：连续格点场、站点降水、台风，以及各自的确定性和集合分支。
- 输入：文件格式、数据源、变量映射、单位和时间语义。
- 处理：时间累积、空间配对、成员处理、参考场、缺测和区域筛选。
- 指标：正常样本、可手算样本、边界条件，以及独立参考值或回归基线的来源。
- 执行：专用串行、通用框架串行、线程、进程和 resume；仅核对已承诺支持的组合。
- 输出：评分 CSV、诊断表、manifest、单次报告及批量报告索引。

验收：逐项标注“已覆盖 / 未覆盖 / 不支持 / 因资料缺失未验证”，
避免以测试文件数量或通过数量代替功能覆盖说明。

### E03：缺少新路径下的完整批量评测范例

用户希望能在一个新的脚本中组织多项评测，保存各项产物，最后导出报告。
当前已有单个 Fengqing 入口和配置，但尚缺面向迁移后全部业务的完整范例。

代码核查：`pipelines/evaluation/cli.py` 已提供 `run_evaluations(configs)`，
配置加载支持 `cfgs` 列表；`reporting.build_report` 支持读取已有 CSV 重建基础报告。
因此工作重点是组合现有能力、补齐批量任务记录和报告索引，而非新建另一套执行框架。

建议在 `examples/evaluation/` 增加一个清晰的批量入口，负责：

1. 接收配置清单及数据、输出位置。
2. 校验配置并展示本次任务列表。
3. 为每个任务建立独立输出目录，执行其评测流程。
4. 记录成功、失败、无有效样本等状态及产物路径。
5. 为具备对应模板的结果生成报告，并标明基础报告与专项分析报告的范围。
6. 生成批量任务清单及报告索引，明确整体完成状态。

“批量评测任务”与“pytest 测试用例”需要分别组织：范例调用正式评测接口，
pytest 验证该接口及产物，不应通过导入 `test_*.py` 来驱动业务。

拟议产物结构，待确认：

```text
results/<batch_id>/
├── tasks.json                 # 任务、配置、状态与产物路径
├── REPORT.md                  # 批量结果与各报告链接
├── <task_id>/
│   ├── scores.csv
│   ├── manifest.json
│   ├── diagnostics/
│   └── report/
└── ...
```

任务完成后应允许仅重新生成报告，无需重新计算评分。
汇总报告先汇总任务状态和链接；跨模型评分比较需单独约定样本与指标口径。

验收：外部用户可按文档修改自己的数据路径，用一条命令完成多任务评测和报告输出；
并能用小型合成资料运行可复现范例。

### E04：DataLoader、文件读取和配置选择耦合

用户指出：不同数据源对应的配置选择和默认函数写死，与之前的 IO 能力可以整合。
口述中的“分期、CRA5”具体指代待确认；检查时以实际配置的 reader 类型为准。

代码核查：通用格点源已复用 `datakit.io.readers` 的布局与读取器，气候态也有
IO 与评测适配的一致性测试。不能将当前状态描述为完全没有整合；应继续处理
专用入口的类型限制，以及部分专用 Reader 的底层读取与适配边界。

重点检查：

- `pipelines/evaluation/components.py` 中数据源工厂与默认布局的绑定。
- `pipelines/evaluation/execution/sources.py` 和
  `datakit/evaluation/adapters/` 与 `datakit/io/readers/` 的职责重叠。
- `serial.py` 中对 Fengqing、CRA 的直接判断及读取器构建。
- 配置中的路径、变量、布局参数能否通过明确接口覆盖，是否需要改函数源码。

拟议职责划分：

| 层次 | 应负责的内容 |
| --- | --- |
| IO | 文件发现、格式解码、资源关闭和底层读写错误。 |
| 数据适配 | 变量映射、单位和时间语义、统一数据契约。 |
| 数据加载 | 根据请求读取范围，管理切片、缓存和驻留。 |
| 配置与工厂 | 显式选择数据源及其参数，验证并构建组件。 |
| 评测流程 | 决定需要哪些数据与如何配对，不重复实现格式读取。 |

区分文件格式与数据产品布局：不同数据源可以共享 NetCDF/GRIB/Zarr 读取能力，
但特有的目录规则、变量和单位语义仍需保留并测试。

验收：同一数据源不重复维护多套读取逻辑；扩展布局或修改数据路径不会迫使用户
改动指标代码；现有 IO 与评测读取的一致性有测试证明。

### E05：变量、指标计算与系统编排重复

用户关注：每个变量或指标的实现是否携带了从头到尾的整套系统，导致重复度较高。
这是待逐项核实的职责问题，不能直接断言每个指标类都包含文件读取或完整编排。

已知需要梳理的部分：

- 通用 Runner 与专用串行入口都有发现、读取、配对、状态合并和落盘步骤。
- 两套入口的指标选择语义不同：通用入口依赖 pipeline 模板，专用串行入口依赖
  `metric_options`。
- 格点、站点、台风各有特定业务处理，但状态累计、运行记录和结果保存可明确复用。

拟议边界：

```text
配置 → 数据加载 → 业务预处理与配对 → EvaluationBatch
                                      ↓
                                  指标计算
                                      ↓
                             状态合并与结果保存
                                      ↓
                                  报告生成
```

指标接收准备好的样本及必要元数据，负责校验、累计和形成评分；
业务预处理负责时间窗口、空间插值、成员及参考场准备；
执行入口负责调用顺序和任务状态。

验收：新增指标可复用现有读取和配对；新增数据源不复制指标公式；
串行与其他执行模式在相同口径下可对表。

## 三、建议推进顺序（待确认）

1. 确认 TY、数据源名称，以及“批量评测”的任务和报告范围。
2. 建立功能—入口—配置—测试—报告覆盖矩阵，明确公共数据契约。
3. 整理 IO、适配和加载的边界，收拢重复数据读取。
4. 明确指标与业务编排的边界，整理串行入口并验证结果一致性。
5. 增加按新接口组织的批量范例、报告索引和报告单独重建入口。
6. 用合成资料形成必跑验证，再用真实资料完成业务和数值验收。

每一步先给出可审查的范围和接口方案，确认后实施；本记录不授权直接修改执行框架。
